# Design

## Context

Мотивация и объём: `proposal.md`, требования: `specs/moex-price-watch/spec.md` и дельта `specs/mcp-server-runtime/spec.md`.

Что важно в текущем устройстве:

- Клиент (бот) запускает сервер по stdio подпроцессом и закрывает его; долгоживущего процесса нет. Поэтому планировщик внутри сервера невозможен: «часы» находятся у клиента, а сервер по его вызову делает всё, срок чего наступил.
- Клиент будет запускать сервер на каждое обращение (таймер, команда пользователя), и обращения могут пересекаться по времени. Общее состояние держится в файле SQLite, а не в памяти процесса.
- Поток вызова инструмента: `server.py` → `tools/*.py` (чистые async-функции `(iss, ...) -> модель`, рядом `DESCRIPTION`) → `IssClient`. Новые инструменты следуют той же схеме; логика расписания выносится в отдельный пакет, чтобы её можно было тестировать без MCP.
- `get_current_price` уже нормализует цену (единицы, задержка, время котировки, статус). Опрос переиспользует его как есть, а не повторяет разбор ISS.
- Все времена, которые видит клиент, в московском поясе (`MSK` из `tools/price.py`); ISS отдаёт их так же.
- Тесты не ходят в сеть (`conftest.py` блокирует сокеты), подмена ISS через `IssClient(transport=...)` и фикстуры. Для расписания добавляется подмена часов.

## Goals / Non-Goals

**Goals:**
- Сервер остаётся «пассивным»: не измеряет время сам, все сроки вычисляются относительно момента вызова `watch_run_due`.
- Целостность данных при пересекающихся вызовах из нескольких процессов.
- Контракт схем инструментов (ниже) достаточен, чтобы писать бота параллельно, не заглядывая в код сервера.
- Режим по умолчанию не меняется: ни новых инструментов, ни файлов.

**Non-Goals:**
- Собственный планировщик, фоновые потоки или демон в сервере.
- Отправка сообщений, знание про Telegram, повторы доставки: это клиент.
- Фильтрация по торговым часам и праздникам (замеры вне сессии сохраняются, цена просто не меняется).
- LLM в сводке; уведомление по порогам изменения цены; время суток и часовые пояса в расписании; аутентификация клиента (сервер локальный, идентификатор чата принимается на веру у того, кто запустил процесс).

## Decisions

### 1. Режим расписания включается флагом `--watch-db`, а не работает всегда

Инструменты расписания принимают `chat_id` от клиента и изменяют состояние; модель их видеть не должна (иначе она может читать и менять расписание чужого чата, подставив другой `chat_id`). Клиент бота запускает для модели сервер без флага, для планировщика с флагом, так что граница проходит по самому процессу, а не только по фильтру на стороне клиента.

Альтернативы: (а) всегда регистрировать и полагаться на allowlist имён в клиенте: одна ошибка в фильтре открывает всё; (б) отдельный пакет/точка входа `mcp-moex-watch`: чище по разделению, но дублирует запуск, `uv`-скрипты и документацию ради того же результата. Клиентский allowlist остаётся вторым рубежом (в задачах бота), но не единственным.

### 2. Инструменты расписания не помечаются `readOnlyHint`

Клиент бота отдаёт модели только инструменты с этим признаком, поэтому признак используется как «безопасно отдавать модели». `watch_status` и `watch_get_report` физически ничего не меняют, но принимают `chat_id` извне и тоже не должны попасть к модели. Это осознанное расширение смысла признака в этом проекте, оно зафиксировано в описаниях инструментов («служебный, для клиента-планировщика»). Признак `idempotent_hint` ставится только там, где повтор вызова не меняет состояние (`watch_stop`, `watch_ack`, `watch_status`, `watch_get_report`); `read_only_hint` у всех шести задан явно как `false`.

### 3. Пассивный сервер: `watch_run_due` + `next_due_at`

```
 клиент: таймер(next_due_at) --> watch_run_due()
   сервер (один вызов):
     1. заявить опросы, срок которых наступил (сдвинуть next_poll_at)   [транзакция]
     2. опросить биржу по уникальным тикерам                           [без транзакции]
     3. записать замеры, если опрос не заменён                         [транзакция]
     4. сформировать сводки, срок которых наступил                     [транзакция]
     5. удалить устаревшее (старше 30 суток)
     6. вернуть неподтверждённые сводки и next_due_at
```

Клиент вызывает инструмент точно в момент `next_due_at` и переставляет таймер по ответу. Пока у клиента нет опросов, `next_due_at = null` и процессы не запускаются вовсе.

Альтернатива: фиксированный тик клиента раз в минуту с запуском процесса каждый раз. Отвергнута из-за лишних ≈0,75 с запуска и запросов впустую; `next_due_at` даёт то же без опроса «вхолостую».

Порядок 1-3-4 важен: шаг 1 заранее сдвигает срок (заявка), поэтому параллельный вызов не опросит те же тикеры второй раз (см. решение 5).

### 4. Хранилище: стандартный `sqlite3`, файл, схема с версией

Новых зависимостей нет. Соединение открывается на операцию и закрывается (процесс всё равно короткоживущий); `journal_mode=WAL`, `busy_timeout` 10 с, `foreign_keys=ON`, версия схемы в `PRAGMA user_version` (создание при первом использовании, при неизвестной более новой версии ошибка, а не порча данных). Вызовы `sqlite3` синхронные, короткие, оборачиваются в `asyncio.to_thread`, чтобы не блокировать цикл во время опроса биржи.

Схема (времена в БД как целые секунды Unix, UTC; наружу отдаются ISO в `+03:00`):

```
watches(chat_id PK, secids TEXT /*JSON*/, poll_seconds, report_seconds,
        poll_interval TEXT, report_interval TEXT,  /* как приняты: "15m" */
        version INTEGER, started_at, window_start /* не включительно */, next_poll_at, next_report_at)
meta(key PK, value INTEGER)                         /* счётчик версий опросов */
observations(id PK, chat_id, version, secid, observed_at, ok INTEGER,
             price REAL NULL, price_unit TEXT NULL, price_source TEXT NULL, quote_at INTEGER NULL)
reports(id PK, chat_id, period_start, period_end, created_at,
        payload TEXT /*JSON: агрегаты и текст*/, delivered_at INTEGER NULL)
индексы: observations(chat_id, observed_at), reports(delivered_at, id)
```

Уточнения, найденные при реализации:

- `version` берётся из общего счётчика в `meta`, а не как `версия + 1`: после `watch_stop` и новой постановки номер не должен совпасть с номером, который заявил ещё идущий `watch_run_due` (иначе его замеры попали бы в новый опрос).
- `window_start` это нижняя граница периода не включительно, при постановке `now - 1`; замер, сделанный в момент границы, входит ровно в одну сводку (иначе при совпадении сроков опроса и сводки каждый граничный замер считался бы в двух сводках). Показываемое начало периода `max(started_at, window_start)`.
- `reports.id` это `AUTOINCREMENT`: идентификаторы не переиспользуются после очистки, и подтверждение старого `report_id` не отметит новую сводку.
- Замеры старше срока хранения не входят в период сводки, даже если очистка (шаг 5, она идёт после формирования сводок) до них ещё не дошла.
- Интервалы хранятся и как секунды, и как принятая строка (`60m` остаётся `60m`), чтобы `watch_status` возвращал их в том же виде, что и `watch_set`.
- В `watch_status.samples_in_period` и `TickerAggregate.samples` считаются только удавшиеся замеры; неудавшиеся отдельно (`failed_samples`).

Неудавшийся замер хранится строкой с `ok = 0`, а не пропадает: сводка обязана показывать число сбоев. `version` растёт при каждой замене опроса (`watch_set`) и привязывает замер к конкретному опросу. Сводка хранится готовой (`payload`), чтобы повторная доставка отдавала тот же текст.

Альтернатива: JSON-файл. Отвергнута: нет атомарности при пересекающихся процессах, а именно она нужна.

### 5. Согласованность: «заявка, опрос, запись с проверкой версии»

- Заявка (шаг 1): в транзакции `BEGIN IMMEDIATE` читаются наступившие опросы и сразу же `next_poll_at = now + poll_seconds`. Второй процесс после этого срока не увидит.
- Запись (шаг 3): замеры вставляются только для строк `watches`, у которых `version` всё ещё прежний. Если опрос заменили или остановили, пока шёл запрос к бирже, замеры выбрасываются.
- Сводка (шаг 4): в транзакции условие `next_report_at <= now` проверяется заново; сводка создаётся и `next_report_at`/`window_start` сдвигаются в той же транзакции, поэтому дубль невозможен.
- Побочный эффект «заявки»: если процесс упал между шагами 1 и 3, один замер потерян. Это допустимо по решению «пропущенные замеры не догоняются».

### 6. Опрос биржи

Для каждого уникального тикера всех опросов, срок которых наступил, вызывается `get_current_price` (кэш `IssClient` 10 с дополнительно защищает от повторов внутри вызова). Одновременных запросов не больше 5 (`asyncio.Semaphore`), чтобы 10 тикеров × несколько чатов не превращались в шквал запросов к публичному API. Любое `MoexError` конкретного тикера превращается в неудавшийся замер; неожиданные исключения не глотаются. Первый замер при `watch_set` идёт тем же кодом, но его ошибки поднимаются (это и есть проверка тикеров).

### 7. Агрегаты и сводка: чистые функции

`watch/report.py` не знает про SQLite и MCP: принимает список замеров и границы периода, возвращает структуру агрегатов и текст. Сравнение по цене в её единицах (для облигаций это проценты от номинала: пересчёт в рубли не нужен, изменение в процентах для процентов от номинала остаётся корректным относительным изменением). Округление: изменение в процентах до 2 знаков, цены как получены (без искусственного округления). Текст — фиксированный шаблон, примерно:

```
Сводка за 26.09 12:00 - 13:00 (МСК)
SBER: 4 замера, 301,2 -> 303,0 (+0,6%), мин 300,9, макс 303,4, котировка на 12:45
GAZP: данных нет (неудавшихся замеров: 4)
Котировки акций, облигаций и фондов задержаны на 15 минут, индексы без задержки. Это не инвестиционная рекомендация.
```

Для облигаций после цены добавляется «% от номинала». Точный русский текст фиксируется в тестах, сверять с ним бота не нужно: бот отправляет `text` как есть.

### 8. Модуль и файлы

```
src/mcp_moex/watch/
  intervals.py   разбор и границы интервалов ("15m" -> секунды)
  store.py       SQLite: схема, транзакции, запросы
  report.py      агрегаты и текст
  service.py     set / stop / status / report / run_due / ack (принимает store, iss, clock)
src/mcp_moex/tools/watch.py   DESCRIPTION-ы и тонкие функции для server.py
```

`create_server(iss=None, watch_db=None, clock=None)`: при `watch_db` регистрирует шесть инструментов и добавляет в `INSTRUCTIONS` фразу о служебной природе. `clock` нужен тестам (по умолчанию текущее время). Новые доменные ошибки (в `errors.py`, на русском, для LLM): «опрос не задан», «хранилище недоступно». Неверные интервалы и число тикеров используют существующее `InvalidArguments`.

### 9. Числовые границы

| Параметр | Значение | Почему |
|---|---|---|
| Период опроса | 5 мин ... 1 сутки | котировки и так задержаны на 15 минут, чаще опрашивать бессмысленно |
| Период сводки | от периода опроса до 7 суток | сводка реже опроса не имеет смысла для агрегатов, недели достаточно |
| Тикеров на чат | 1...10 | ограничивает нагрузку на ISS и размер сводки в одном сообщении Telegram |
| Срок хранения | 30 суток | покрывает максимальный период сводки с запасом, диск не растёт |
| Сводок за вызов | до 100, старые первыми, признак `has_more` | защита от неподтверждаемых сводок, накопившихся у заблокированных чатов |
| Параллельные запросы | 5 | вежливость к публичному API |

Значения заданы константами; в конфигурацию не выносятся.

## Контракт инструментов (шов с бот-репозиторием)

Идентификатор чата `chat_id` — целое число. Все времена — строки ISO 8601 в `+03:00`. Интервалы возвращаются в том же виде, в каком приняты (без пробелов, в нижнем регистре).

| Инструмент | Вход | Результат |
|---|---|---|
| `watch_set` | `chat_id`, `secids: [str]` (1...10), `poll_interval: str`, `report_interval: str` | `{chat_id, secids, poll_interval, report_interval, replaced: bool, next_poll_at, next_report_at, first_samples: [{secid, price, price_unit, quote_at}]}` |
| `watch_stop` | `chat_id` | `{chat_id, stopped: bool}` |
| `watch_status` | `chat_id` | `{active: false}` или `{active: true, chat_id, secids, poll_interval, report_interval, started_at, next_poll_at, next_report_at, samples_in_period: int, pending_reports: int}` |
| `watch_get_report` | `chat_id` | `Report` с `report_id = null` |
| `watch_run_due` | нет | `{now, next_due_at: str \| null, polled: {chats, tickers, failed}, reports: [Report], has_more: bool}` |
| `watch_ack` | `report_ids: [int]` | `{acknowledged: int}` |

```
Report = {report_id: int | null, chat_id, period_start, period_end, text: str,
          tickers: [{secid, samples: int, failed_samples: int,
                     first_price, last_price, change_percent, min_price, max_price,
                     price_unit, last_quote_at}]}   # поля с ценами null, если замеров нет
```

Ошибки — обычные результаты инструмента с `isError = true` и русским текстом. Бот должен: вызывать `watch_ack` только после успешной отправки; повторять `watch_run_due` без ожидания, пока `has_more = true`; на «Forbidden» от Telegram вызывать `watch_stop` для чата.

## Risks / Trade-offs

- [Клиентская ошибка выдаёт модели инструменты расписания] → сервер без флага их не публикует; клиентский allowlist как второй рубеж (в изменении бота).
- [Потеря замера при падении между заявкой и записью] → допустимо (замеры не догоняются); сводка честно показывает число замеров.
- [Долгий `watch_run_due` при многих чатах и тикерах превысит тайм-аут клиента (в боте `MCP_TIMEOUT_SECONDS` = 60)] → ограничение 5 параллельных запросов, кэш, уникальные тикеры; худший случай (десятки чатов) фиксируется как известное ограничение, а не решается сейчас.
- [Файл хранилища растёт] → удаление старше 30 суток при каждом `watch_run_due`; объём при 10 тикерах на 5 минутах ≈ 3 тыс. строк в сутки на чат.
- [Вне торговой сессии сводка «нулевая» (цена не менялась)] → в v1 сознательно не фильтруем; время последней котировки в сводке показывает, что данные не обновлялись.
- [Расширение смысла `readOnlyHint`] → зафиксировано в описаниях и в этом документе; при появлении настоящего признака «безопасно для модели» в протоколе перейти на него.
- [Идентификатор чата принимается на веру] → сервер локальный, запускается только оператором и ботом; данные не чувствительные (тикеры и цены), но сам `chat_id` идентификатор пользователя: файл хранилища не должен попадать в git (решает каталог, который выбирает бот).

## Migration Plan

Миграции нет: без `--watch-db` поведение прежнее, новых зависимостей нет. Включение: клиент добавляет флаг при запуске для планировщика. Откат: убрать флаг; файл хранилища можно оставить или удалить, других побочных эффектов нет. Схема версионируется через `user_version` на будущее.

## Open Questions

- Формат вывода чисел в тексте сводки (разделитель дробной части, число знаков у цен): уточняется при реализации на реальных примерах и фиксируется тестами, на контракт не влияет.
