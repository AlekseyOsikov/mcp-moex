# Proposal

## Why

Сервер сегодня отвечает только на разовые вопросы: цену можно узнать «сейчас», но нельзя накапливать её во времени. Агенту-консультанту нужна регулярная сводка по выбранным бумагам («что было с SBER и GAZP за последний час»), а для этого кому-то надо опрашивать биржу по расписанию, сохранять замеры и считать по ним агрегаты. Серверная часть такого планировщика: хранилище, опрос, агрегаты и готовый текст сводки. Часы и доставку сообщений берёт на себя клиент (Telegram-бот) отдельным изменением в своём репозитории.

## What Changes

- Новый режим сервера, включаемый явно (`--watch-db <путь к SQLite-файлу>`): к трём существующим инструментам добавляются инструменты расписания. Без флага сервер работает ровно как раньше: три инструмента, только чтение, без файлов на диске.
- Инструменты расписания: `watch_set` (задать или заменить опрос чата: тикеры, период опроса, период сводки), `watch_stop`, `watch_status`, `watch_get_report` (агрегаты по накопленному без отправки), `watch_run_due` (выполнить всё, что пора: опрос ISS, формирование сводок; вернуть сводки к отправке и время следующего срока) и `watch_ack` (подтвердить доставку сводок).
- Замеры и сводки хранятся в SQLite и переживают перезапуск. Замеры и готовые сводки удаляются по истечении срока хранения.
- Агрегаты по каждому тикеру считает код: первая и последняя цена, изменение в процентах, минимум, максимум, число замеров. Сводка — шаблонный русский текст без LLM с пометкой о задержке котировок и о том, что это не рекомендация.
- Периоды задаются интервалами (`15m`, `1h`, `1d`), не временем суток. Есть нижняя граница периода опроса, верхняя граница числа тикеров на чат и срок хранения (числа в `design.md`).
- Доставка сводок двухфазная: сервер считает сводку доставленной только после `watch_ack`, поэтому сбой отправки не теряет её.
- Инструменты расписания НЕ помечаются `readOnlyHint`: они изменяют состояние и принимают `chat_id` от клиента, а не от модели. Вместе с включением только по флагу это удерживает их вне набора инструментов, который получает модель.
- **BREAKING**: нет. Поведение сервера по умолчанию и контракты трёх существующих инструментов не меняются; меняется формулировка требований «ровно три инструмента, все только читающие», которые теперь относятся к режиму по умолчанию.

## Capabilities

### New Capabilities
- `moex-price-watch`: постановка и остановка опроса цен по тикерам для чата, хранение замеров, выполнение опроса по срокам, агрегаты и шаблонная сводка, доставка сводок с подтверждением.

### Modified Capabilities
- `mcp-server-runtime`: регистрация инструментов (три по умолчанию, дополнительные инструменты расписания только в явном режиме и без признака «только чтение») и запуск (новый необязательный флаг `--watch-db`).

## Impact

- Код: новый пакет `src/mcp_moex/watch/` (хранилище, интервалы, агрегаты, сервис), новый `src/mcp_moex/tools/watch.py` с описаниями инструментов, правки `server.py` (флаг, регистрация) и `models.py` (входные параметры и результаты).
- Зависимости: только стандартная библиотека (`sqlite3`); новых пакетов нет.
- Диск: файл SQLite по пути из флага; в режиме по умолчанию ничего не пишется.
- Документация: `README.md` и `CLAUDE.md` (в них говорится о трёх инструментах только для чтения).
- Внешние системы: запросы к ISS теми же средствами, что и `get_current_price`.
- Смежное изменение (другой репозиторий, создаётся отдельно): бот запускает сервер в режиме `--watch-db`, вызывает эти инструменты напрямую по таймеру и в командах, доставляет сводки в чат. Схемы инструментов, зафиксированные в `design.md`, являются швом между двумя изменениями.
