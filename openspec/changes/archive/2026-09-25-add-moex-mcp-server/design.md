# Design

## Context

Проект `mcp-moex` пустой: кода нет, есть только каркас OpenSpec. Окружение: Python 3.12.3, `uv`; пакеты `mcp` и `httpx` не установлены. ISS (`https://iss.moex.com/iss`) проверен с этой машины и отвечает без ключа. Мотивация и границы изменения в `proposal.md`, поведение в `specs/`.

Сведения об ISS, проверенные на живых запросах и лежащие в основе решений:

- Котировки акций, облигаций и фондов задержаны на 15 минут: в `marketdata` `SYSTIME` опережает `UPDATETIME` ровно на 900 секунд (поле `TIME` это время последней сделки и может быть старше). Индексы задержки не имеют: у `IMOEX2` и `RGBI` `TIME` равно `SYSTIME`. Все времена в московском часовом поясе.
- Один и тот же тикер присутствует на десятках площадок (у `SBER` 51 запись в `boards`). Основная помечена `is_primary = 1` (`TQBR`, `TQOB`, `SNDX`); у `TMOS` площадка `TQTF` пуста, а основная это `TQBR`.
- Неизвестный тикер не даёт ошибки: ISS отвечает `HTTP 200` с пустыми таблицами. Регистр тикера ISS не различает.
- Свечи: интервалы `60`, `24`, `7`, `31` работают; не больше 500 строк за запрос; постраничность через `start`. Интервал `4` за проверенный период вернул 0 строк, поэтому не используется.
- Цены облигаций (и в `marketdata`, и в свечах) в процентах от номинала; `ACCRUEDINT` в валюте номинала; код валюты рубля `SUR`. У индексов объём в свечах равен 0.
- Поиск `/securities.json` не ранжирует, отдаёт до 100 строк, и серверные фильтры `is_trading=1` и `group_by`/`group_by_filter` радикально убирают шум. Группа `stock_etf` существует отдельно от `stock_ppif`. Среди индексов часть основных площадок `SNDX`, часть `RTSI`, плюс шум на `INAV` и `INPF`.

## Goals / Non-Goals

**Goals:**
- Агент вызывает три инструмента по `stdio` и получает типизированный результат с однозначными единицами.
- Внутреннее устройство ISS (движки, рынки, площадки, колонки) не просачивается в контракт инструментов.
- Ответы компактны для контекста LLM, а расчёты (пересчёт облигаций, сводка) делает сервер, а не модель.

**Non-Goals:**
- Реальное время, стаканы, сделки, дивиденды, купонные календари, фундаментальные данные.
- Кэш между перезапусками, база данных, фоновые задачи.
- Авторизация, TLS, деплой: сервер локальный.
- Корректировка истории на сплиты и дивиденды.

## Decisions

### Структура пакета

```
mcp-moex/
  pyproject.toml                (uv, скрипт mcp-moex)
  src/mcp_moex/
    server.py     MCPServer: регистрация инструментов, транспорты, main()
    iss.py        тонкий async-клиент ISS: GET, ретраи, кэш, разбор columns/data
    errors.py     доменные ошибки с текстами для агента
    resolver.py   secid -> Instrument(engine, market, board, group, asset_type, currency)
    models.py     Pydantic-модели входов и выходов
    tools/
      search.py   search_securities
      price.py    get_current_price
      history.py  get_price_history
  scripts/smoke_client.py       смоук-клиент на MCP SDK
  tests/                        юнит-тесты на записанных ответах ISS
```

Поток вызова:

```
tool call --> resolver.resolve(secid) --> Instrument{engine,market,board,asset_type}
                     |                         |
                     |  /securities/{secid}    v
                     |  (кэш: долго)     iss.get(marketdata | candles)
                     v                         |
              нормализация по asset_type <-----+
                     |
                     v
              Pydantic-модель --> structuredContent + text JSON
```

### Решение 1. `MCPServer` из официального `mcp` SDK, модели Pydantic для входа и выхода

Параметры инструментов описываются аннотациями и `Field(description=...)`, тогда `MCPServer` сам генерирует `inputSchema`; тип возврата даёт `outputSchema` и `structuredContent`. Это прямо закрывает пункты задания «регистрация» и «описание входных параметров».
Версия SDK: `mcp` 2.x (на момент реализации 2.2.0), где прежний `FastMCP` из 1.x переименован в `MCPServer` (`from mcp.server.mcpserver import MCPServer`). Зависимость ограничена диапазоном `mcp>=2.2,<3`. Протокол обмена остаётся прежним, поэтому агент на другой версии SDK подключается по `stdio` без изменений; совместимость с клиентом 1.x проверяется на приёмке.
*Альтернативы:* низкоуровневый `Server` из SDK (больше кода без выгоды); сторонний `fastmcp` (лишняя зависимость, а агент использует официальный SDK); закрепить `mcp<2` и `FastMCP` 1.x (отвергнуто: новый проект не должен стартовать на предыдущей мажорной версии).

### Решение 2. Транспорт: `stdio` по умолчанию, Streamable HTTP только на `127.0.0.1`

Агент на Python и MCP SDK запускает сервер сам через `stdio_client`. Не нужны порты, токены и отдельный процесс. HTTP оставлен ключом командной строки для отладки и запуска независимо от агента; привязка только к loopback исключает случайную публикацию наружу. Порт задаётся ключом `--port` (по умолчанию 8000); адрес всегда `127.0.0.1` и не настраивается.
*Альтернатива:* только HTTP, отвергнута: добавляет сетевую поверхность без пользы. SSE-транспорт не используется, он устарел в спецификации MCP.

### Решение 3. Резолвер по `is_primary` с кэшем

`resolver` запрашивает `/securities/{secid}.json` (таблицы `description` и `boards`), берёт запись с `is_primary = 1` для движка `stock` и по таблице групп определяет `asset_type`:

| Группа ISS | asset_type |
|---|---|
| `stock_shares`, `stock_dr` | `stock` |
| `stock_bonds` | `bond` |
| `stock_ppif`, `stock_etf` | `fund` |
| `stock_index` | `index` |
| остальные | неподдерживаемо, ошибка |

Пустые таблицы дают «не найдено». Результат резолвинга кэшируется надолго (состав площадок меняется редко), при этом каноническое написание `secid` берётся из ответа. Вместо жёсткой таблицы `тикер -> площадка` (`TQBR`, `TQOB`...) решение опирается на данные ISS, поэтому новые бумаги работают без правок кода.
*Альтернатива:* угадывать площадку перебором, отвергнута: лишние запросы и неоднозначность.

### Решение 4. Единицы и нормализация по классу актива

- `stock`, `fund`: `price = LAST`, иначе `PREVPRICE` (`price_source = "previous_close"`); единица это валюта бумаги, где `SUR` нормализуется в `RUB`.
- `bond`: `price = LAST` в `percent_of_face`; `price_rub = price / 100 * FACEVALUE`; `dirty_price = price_rub + ACCRUEDINT`; `yield_percent = YIELD`. Для облигаций с номиналом в другой валюте используется `FACEUNIT`.
- `index`: `price = CURRENTVALUE`, `points`.
- `as_of`: дата из `SYSTIME` и время `TIME`, оформленные как ISO 8601 с `+03:00` (если получилось позже `SYSTIME`, значит `TIME` относится к предыдущим суткам). Для цены предыдущего закрытия `as_of` это конец дня `PREVDATE` (`T23:59:59+03:00`).
- Задержка задаётся константами по классу актива, так как ISS отдаёт данные без подписки: `delayed = true`, `delay_minutes = 15` для акций, облигаций и фондов; `delayed = false`, `delay_minutes = 0` для индексов. Вычислять задержку из `SYSTIME - TIME` нельзя: `TIME` у малоликвидных бумаг это время последней сделки, оно бывает старше на часы.
- В истории облигации не пересчитываются в рубли: номинал амортизируемых бумаг меняется, и пересчёт по текущему номиналу дал бы неверные значения задним числом.

### Решение 5. История: свечи ISS с полной выборкой и серверной сводкой

Источник это эндпоинт свечей, а не `history`: он даёт единый интерфейс для акций, облигаций, фондов и индексов и поддерживает часовой интервал. Отображение `hour -> 60`, `day -> 24`, `week -> 7`, `month -> 31`. Сервер листает страницы (`start += 500`) до конца периода, но не более 10 страниц (до 5000 свечей); если этого не хватает, возвращает ошибку с советом взять более крупный интервал. `summary` считается по всем свечам, а в `candles` отдаются последние 300 (`candles_truncated`, `candles_returned`).
Свечи содержат и выходные сессии (например, суббота 2026-09-05 у `SBER`); это принимается как есть. Параметр `till` ISS включает весь последний день (у часовых свечей все 18 часов), а недельные и месячные свечи попадают в выборку по дате начала (неделя с 31 августа не входит в период с 1 сентября); об этом сказано в описании инструмента.
*Альтернатива:* эндпоинт `history` (дневные итоги, ровно 100 строк на страницу, нет часового интервала). Отвергнута: меньше единообразия.

### Решение 6. Поиск: серверные фильтры ISS плюс постобработка

Запрос идёт с `is_trading=1`, для конкретного `asset_type` с `group_by=group` и `group_by_filter=<группа>`; для типов с несколькими группами (`stock`, `fund`) выполняется по запросу на группу и результаты объединяются. Для `any` берутся все четыре класса. Далее постфильтр: отбрасываются площадки `INAV` и `INPF`, а для `index` оставляются только `SNDX` и `RTSI`; точное совпадение `secid` или ISIN (без регистра) поднимается вверх; результат обрезается по `limit` с признаком `truncated`. Наружу отдаётся нормализованный `asset_type`, а не группа ISS.
*Альтернатива:* локальный индекс всех бумаг с собственным ранжированием. Отвергнуто: сложнее, нужна синхронизация и хранение.

### Решение 7. HTTP-клиент, кэш и повторы

Один общий `httpx.AsyncClient` (таймауты, `iss.meta=off`, узкие `iss.only` и `*.columns` для уменьшения ответов) с `trust_env=False`: ISS публичен и проверен с этой машины напрямую, а прокси из окружения (на машине разработки задан `ALL_PROXY=socks://127.0.0.1:2080`, который `httpx` не принимает) ронял бы создание клиента. Поддержка прокси не входит в изменение; при необходимости её добавляет отдельным явным параметром. Кэш в памяти с TTL: котировки 10 секунд (данные и так задержаны на 15 минут, а кэш защищает от лавины вызовов агента), резолвер и справочные данные подолгу. Повтор 1–2 раза с задержкой на сетевые ошибки и статусы 5xx и 429, затем ошибка инструмента. Кэш не переживает перезапуск.

### Решение 8. Ошибки и логи

Доменные исключения (`SecurityNotFound`, `UnsupportedAssetClass`, `RangeTooLarge`, `IssUnavailable`, а также `MarketDataUnavailable` для бумаг без котировок и `InvalidArguments` для неверных по смыслу аргументов) преобразуются в ошибки инструмента (`isError`) с понятным текстом на русском: что случилось и что делать. Трассировки не отдаются. Логирование только в stderr (`logging` с `stream=sys.stderr`); в коде запрещён `print` в stdout.

### Решение 9. Тесты и смоук-клиент

Юнит-тесты работают на записанных ответах ISS (фикстуры), без сети: разбор колонок, резолвер, пересчёт облигаций, сводка, пагинация, фильтры поиска. Смоук-клиент `scripts/smoke_client.py` использует `stdio_client` и `ClientSession` из `mcp`, запускает `uv run mcp-moex`, вызывает `list_tools` и три инструмента на реальных данных и завершается ненулевым кодом при сбое. Он же служит образцом подключения для проекта агента.

## Risks / Trade-offs

- **Формат ISS может измениться, а границы недокументированы** → тонкий клиент, разбор колонок по именам, юнит-тесты на фикстурах, короткий кэш, ретраи и явная ошибка при недоступности.
- **Задержка 15 минут** → явные `delayed`, `delay_minutes` и `as_of` в каждом ответе, описание инструмента прямо говорит, что это не реальное время.
- **Ошибки в единицах облигаций (проценты против рублей)** → явное поле `price_unit`, готовые `price_rub` и `dirty_price`; тесты на ОФЗ.
- **Индексы на площадке `RTSI` не проверены**: URL свечей и `marketdata` проверены только для `SNDX` (`IMOEX`) → на этапе реализации проверить, например, `IMOEXCNY`; при отличии добавить обработку либо ограничить `index` площадкой `SNDX`.
- **Цены истории не скорректированы на сплиты** (проверено на живом ISS: у `BELU` месячное закрытие 5595 в мае 2024 и 676 в сентябре 2024, сплит 1:8) → предупреждение в описании `get_price_history`. Остаточный риск: `summary` (изменение за период, минимум, максимум) по периоду со сплитом искажён и выглядит авторитетно; автоматическое обнаружение скачков не входит в изменение.
- **Общий размер ответа истории** → лимит 300 свечей и сводка по всему периоду; если этого мало для агента, число легко настроить (константа).
- **Число классов ISS шире, чем поддерживается** (депозитарные расписки, иностранные бумаги, еврооблигации) → в поиске они отсутствуют, а прямой запрос цены даёт понятную ошибку о неподдерживаемом классе.
- **Смешение торговых сессий в свечах** (утренняя, основная, вечерняя и выходные) → принимается как есть; `begin` даётся в московском времени.
